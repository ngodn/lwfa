# iPadOS 26 SwiftUI + Liquid Glass: engineering reference (Swift 6.3, iOS 26.5 SDK, no Xcode)

Method note: Apple's doc pages are JS-rendered, so every signature and availability below was pulled from Apple's DocC JSON (`developer.apple.com/tutorials/data/documentation/...json`) and its SwiftUI symbol index, cross-checked against WWDC25 transcripts (219, 256, 282, 323, 356), WWDC26 269, HIG pages, and the blogs named in the brief. One caveat that matters for you: Apple's docs are now rendered from the Xcode 27 SDK. Where a declaration shows `@ContentBuilder` or a `task(id:name:...)` overload, that is the iOS 27 spelling; with the iOS 26.5 SDK the builder is `@ViewBuilder` and `task` is `task(id:priority:_:)`. The behaviour is identical; only the rendered spelling differs. iOS 27-only symbols that sit next to iOS 26 ones in the docs are flagged explicitly.

## 1. Custom Liquid Glass: `glassEffect`, `Glass`, containers, morphing

**Signatures (all iOS/iPadOS 26.0, also macOS/tvOS/watchOS/Catalyst 26; not visionOS)**

```swift
extension View {
  nonisolated func glassEffect(_ glass: Glass = .regular,
                               in shape: some Shape = DefaultGlassEffectShape()) -> some View
  nonisolated func glassEffectID(_ id: (some Hashable & Sendable)?, in namespace: Namespace.ID) -> some View
  @MainActor @preconcurrency func glassEffectUnion(id: (some Hashable & Sendable)?, namespace: Namespace.ID) -> some View
  @MainActor @preconcurrency func glassEffectTransition(_ transition: GlassEffectTransition) -> some View
}
struct Glass {
  static var regular: Glass; static var clear: Glass; static var identity: Glass
  func tint(_ color: Color?) -> Glass
  func interactive(_ isEnabled: Bool = true) -> Glass
}
struct DefaultGlassEffectShape   // a capsule; never instantiate it yourself
@MainActor @preconcurrency struct GlassEffectContainer<Content: View> {
  init(spacing: CGFloat? = nil, @ViewBuilder content: () -> Content)
}
struct GlassEffectTransition { static var identity, matchedGeometry, materialize }
```

**`isEnabled:` does not exist on `glassEffect` in the shipping SDK.** The WWDC25 beta-1 docs (and blogs copying them, e.g. Hacking with Swift and ioscompatibility.com) show `glassEffect(_:in:isEnabled:)`; Apple's current docs and symbol index list only `glassEffect(_:in:)`. The on/off switch is `Glass.interactive(_:)` for interactivity and `.identity` for the whole effect: `.glassEffect(isOn ? .regular : .identity)` (this is the pattern Swift with Majid uses). `backgroundExtensionEffect(isEnabled:)` and `hoverEffect(_:isEnabled:)` do have the parameter.

**Semantics from Apple's docs**
- The modifier renders a shape anchored behind the view with the material and applies Liquid Glass foreground effects over the view's content. The shape fills the view's full frame including padding, so `.padding()` goes before `.glassEffect()`. Apply `glassEffect` after every other modifier that affects appearance; it captures the content to hand to the container.
- `.clear`: Apple's own doc says add a dimming layer beneath, e.g. `.glassEffect(.clear).background(.black.opacity(0.3))`. HIG: 35 percent dark dimming when the underlying content is bright; none needed over dark content or when AVKit playback controls already dim.
- `interactive()` gives the scale/bounce/shimmer that system buttons and sliders have; use it on custom controls and on containers holding interactive elements.
- `GlassEffectContainer`: every glassEffect inside contributes a shape; they render as one set, which is both a performance optimisation and what enables blending and morphing. `spacing` is the distance at which two shapes start merging; if it is larger than the interior HStack/VStack spacing, shapes blend at rest. Glass cannot sample other glass, so nearby glass elements in different containers render inconsistently. Put the whole floating control cluster in one container.
- `glassEffectUnion` merges shapes that share id, shape, and Glass variant into one shape at rest (useful for `ForEach`-generated items or items not in one stack).
- `glassEffectID` + `@Namespace` drive morph animations on insert/remove; `glassEffectTransition` picks the transition. Default within the container's spacing is `.matchedGeometry`; use `.materialize` for elements farther apart than the spacing. Both modifiers only affect view-hierarchy transitions or animations, so wrap the state change in `withAnimation`.

**Rules (HIG Materials, WWDC25 219 and 356, Adopting Liquid Glass)**
- Glass is the floating navigation and control layer only. "Don't use Liquid Glass in the content layer"; use standard materials (`.regularMaterial` etc.) there. Exception: transient interactive elements such as slider knobs.
- "Always avoid glass on glass." Top elements on a glass surface use fills, transparency, and vibrancy, not another glass effect.
- `.regular` is the default everywhere; `.clear` only when all three hold: over media-rich content, a dimming layer is acceptable, and the content on top is bold and bright. Never mix the two variants in one UI.
- Tint only to convey meaning (primary action, status). Tinting everything makes nothing stand out.
- Use sparingly; too many effects or too many containers degrade performance. Limit the on-screen count.

## 2. Buttons, toolbars, tabs, search, sidebars, edge effects

**Button styles (iOS 26.0)**
- `PrimitiveButtonStyle.glass: GlassButtonStyle`, `.glassProminent: GlassProminentButtonStyle`, and `static func glass(_ glass: Glass) -> Self` (e.g. `.buttonStyle(.glass(.clear))`, `.glass(.regular.tint(.blue))`). `GlassButtonStyle.init(_ glass: Glass)` is **iOS 26.1**.
- `buttonBorderShape(_ shape: ButtonBorderShape)` (iOS 15): `.automatic`, `.capsule`, `.circle`, `.roundedRectangle`, `.roundedRectangle(radius:)`. Docs say it affects `.bordered` and `.borderedProminent`; I could not confirm from Apple text that glass styles honour it, though community samples use `.buttonBorderShape(.circle)` with `.glass`. If you need a guaranteed shape, use `.glassEffect(in: .circle)` on a `.plain` button.
- `controlSize(.extraLarge)` exists (iOS 17); iOS 26 adds an X-Large treatment for prominence. `buttonSizing(_:)` is new in iOS 26 (cases not verified here).

**Toolbars (iOS 26.0; ToolbarSpacer and sharedBackgroundVisibility are iOS/iPadOS/Catalyst/macOS only)**
- Items are auto-grouped on one shared glass background; the back button gets its own group. `ToolbarItemGroup(placement:)` groups explicitly.
- `struct ToolbarSpacer { init(_ sizing: SpacerSizing = .flexible, placement: ToolbarItemPlacement = .automatic) }`, `SpacerSizing.fixed / .flexible`. `.fixed` splits one glass group into two; `.flexible` pushes groups apart. Works in customizable `.toolbar(id:)` too.
- `ToolbarContent.sharedBackgroundVisibility(_ visibility: Visibility) -> some ToolbarContent`: `.hidden` removes the glass platter from that item and puts it in its own group (avatar, status view).
- Prominent action: `.buttonStyle(.borderedProminent).tint(.pink)` on the toolbar button; tint only for meaning. Icons render monochrome; `.badge(_:)` works on toolbar buttons.
- Remove any custom bar backgrounds; `toolbarBackground(_:for:)` (iOS 16) and `toolbarBackgroundVisibility(_:for:)` (iOS 18) still exist but Apple says custom backgrounds "will interfere with" the glass and the scroll edge effect. `toolbar(.hidden, for:)` hides bars.
- `navigationSubtitle(_:)` is iOS/iPadOS 26.0.
- **iOS 27 only, will not compile against the 26.5 SDK:** `ToolbarItemPlacement.topBarPinnedTrailing`, `ToolbarOverflowMenu`, `visibilityPriority(_:)` (iOS 27; macOS 26.1), `toolbarMinimizeBehavior(_:for:)`, `Tab(role: .prominent)`, `GeometryProxy.concentricCornerRadii(in:)`, the `@State` macro and `@ContentBuilder`.

**Tab bar**
- `tabBarMinimizeBehavior(_ behavior: TabBarMinimizeBehavior)` (iOS 26): `.automatic`, `.never`, `.onScrollDown`, `.onScrollUp`. Docs describe it as an iPhone behaviour.
- `tabViewBottomAccessory(@ViewBuilder content:)` (iOS 26.0, iOS/iPadOS/Catalyst) and `tabViewBottomAccessory(isEnabled: Bool, content:)` (**iOS 26.1**, for show/hide; conditionally emitting the view leaves an empty slot on 26.0). Read `@Environment(\.tabViewBottomAccessoryPlacement)` (`TabViewBottomAccessoryPlacement?`, `.inline` when the bar is collapsed, `.expanded` otherwise) and switch layouts.
- Search tab: `Tab(role: .search) { ... }` (init is iOS 18) plus `.searchable` on the `TabView`; on iOS 26 the tab is separated at the trailing end and morphs into the search field. `tabViewSearchActivation(_ activation: TabSearchActivation)` (iOS 26) with `.searchTabSelection` activates search on tab selection.
- `tabViewStyle(.sidebarAdaptable)` (iOS 18): on iPadOS a top tab bar that adapts to a sidebar; `tabViewSidebarHeader(content:)` adds a header.
- `.tabItem` is the legacy path; use `Tab` to get the new interactions (Majid).

**Search placement**: with `.searchable`, iPad and Mac put the field top-trailing in the toolbar; iPhone puts it in the bottom bar. `searchToolbarBehavior(_ behavior: SearchToolbarBehavior)` (iOS 26; cases `.automatic`, `.minimize`; Apple's doc sample mistakenly writes `.minimized`) goes after `.searchable` and collapses the field into a button.

**Sidebars and edge effects**
- `NavigationSplitView` on iPadOS 26 gets a floating, inset glass sidebar; scroll views extend beneath it by default; `.inspector(isPresented:)` gets subtler layering. Larger glass surfaces (sidebars, menus) don't flip light/dark; bars and tab bars do.
- `backgroundExtensionEffect()` and `backgroundExtensionEffect(isEnabled: Bool)` (iOS 26): mirrors and blurs the view into adjacent safe areas so a hero image appears to continue under the sidebar/inspector; clips the view; use on one background per screen.
- `scrollEdgeEffectStyle(_ style: ScrollEdgeEffectStyle?, for edges: Edge.Set)` (iOS 26): `.automatic`, `.soft` (blur fade, default under glass bars), `.hard` (nearly opaque linear boundary, for dense floating UIs). `scrollEdgeEffectHidden(_ hidden: Bool = true, for edges: Edge.Set = .all)` removes it.
- `safeAreaBar(edge:alignment:spacing:content:)` (iOS 26) mirrors `safeAreaInset` but insets the safe area and wires the scroll edge effect to the bar. Verified overload: `edge: HorizontalEdge, alignment: VerticalAlignment = .center, spacing: CGFloat? = nil`; the vertical-edge overload presumably mirrors it (not verified). Known issue in 26.1 release notes: `@FocusState` doesn't work inside `safeAreaBar`.

## 3. Sheets, popovers, menus, custom floating controls, concentric corners

- Sheets: on iOS 26 a sheet with at least one partial detent (`presentationDetents([.medium, .large])`, `.height(n)`) floats inset from the screen edges with rounded, device-concentric corners and a glass background; at `.large` it becomes opaque and anchors to the edges. Drop `presentationBackground(_:)` / `presentationBackground(alignment:content:)` (iOS 16.4) so the system material shows. `presentationCornerRadius(_:)` (iOS 16.4) and `presentationSizing(_:)` (iOS 18, `.page`, `.form`, `.fitted`, `.sticky`) still apply. A `Form`/`List` inside the sheet paints its own background; hide it with `.scrollContentBackground(.hidden)` to let the glass through (nilcoalescing).
- Morph from the presenting control: `matchedTransitionSource(id:in:)` on the toolbar button and `.navigationTransition(.zoom(sourceID:in:))` on the sheet root (iOS 18 APIs; the toolbar must live inside a `NavigationStack`/`NavigationSplitView`). Menus, alerts, popovers, and confirmation dialogs morph out of glass controls automatically. Popovers on iPad also get glass; forum reports say glass inside a popover launched from a glass container can fail to render, so don't nest.
- Custom floating control that looks native: a `Button` with `.buttonStyle(.glass)` or a view with `.padding().glassEffect(.regular.interactive())` (capsule by default), placed with `.safeAreaBar` or `.overlay(alignment:)`, all sibling controls wrapped in one `GlassEffectContainer(spacing:)`, plus `.hoverEffect()` for pointer users and `.keyboardShortcut`.
- Concentric corners (iOS 26.0): `ConcentricRectangle` (`init()`, `init(corners: Edge.Corner.Style, isUniform: Bool = false)`, per-corner and `uniformTopCorners:`/`uniformBottomCorners:` inits), and the static `Shape.rect(corners: Edge.Corner.Style, isUniform: Bool = false)` plus per-corner `rect(topLeadingCorner:...)` variants. `Edge.Corner.Style` cases: `.concentric`, `.concentric(minimum: Edge.Corner.Style? = nil)`, `.fixed(_ radius: CGFloat)`, and it is `ExpressibleByIntegerLiteral`/`FloatLiteral` so `corners: 12` compiles. Radius = container radius minus inset; zero means square, so use `.concentric(minimum: 16)` as the standalone fallback (WWDC 356's "concentric with fallback" trick). `containerShape(_ shape: some RoundedRectangularShape)` sets the container for a subtree; `RoundedRectangularShape` (iOS 26) is adopted by `RoundedRectangle`, `Capsule`, `Circle`, `Rectangle`, `ConcentricRectangle`. `ContainerRelativeShape` (iOS 14) still exists and now inherits the container. **`.containerConcentric` (seen in WWDC 323) never shipped**; the final name is `.concentric`. Typical: `.background(.tint, in: .rect(corners: .concentric(minimum: 12)))` or `.glassEffect(in: .rect(corners: .concentric, isUniform: true))`.

## 4. Typography and colour on glass

- Fonts: SF Pro is the system font on iPadOS; use text styles (`.font(.body)`, `.title`, `.headline` ...) for Dynamic Type; `Font.Design` has `.default`, `.monospaced`, `.rounded`, `.serif` (New York), so `.font(.system(.body, design: .rounded))` and `.font(.system(.title2, design: .rounded, weight: .semibold))` are correct. HIG: avoid Ultralight/Thin/Light; prefer Regular through Bold. iOS 26 tightened typography (bolder, left-aligned in alerts and onboarding).
- Text and symbols on glass automatically use a vibrant colour that adapts to the content behind, and flip light/dark with the bar (small surfaces only). Don't set explicit text colours on glass unless conveying meaning; use `foregroundStyle(.primary/.secondary/.tertiary)` hierarchical styles, which resolve to the vibrant label colours over materials.
- Colour: glass has no inherent colour and picks up the content; `Glass.tint(_:)` produces a tonal range mapped to the brightness underneath (stained-glass model), reserved for primary actions and status. Apply colour to the background of one prominent control, not to symbols of many. Prefer system semantic colours (`Color.primary`, `.accentColor`, `.tint`, `.background` styles); if you define custom colours, ship light, dark, and increased-contrast variants even if the app is single-appearance, because glass adaptivity uses them.
- Dark mode: `@Environment(\.colorScheme)`, `preferredColorScheme(_:)` at the presentation root; glass adapts on its own. iOS 26.1 added a user preference (Settings > Display & Brightness > Liquid Glass: Clear or Tinted) that makes glass more opaque system-wide; nothing to do, but test both.

Sources: [HIG Typography](https://developer.apple.com/design/human-interface-guidelines/typography), [HIG Color](https://developer.apple.com/design/human-interface-guidelines/color), [HIG Materials](https://developer.apple.com/design/human-interface-guidelines/materials), [Font.Design](https://developer.apple.com/documentation/swiftui/font/design), [WWDC25 219](https://developer.apple.com/videos/play/wwdc2025/219/), [iOS 26.1 Liquid Glass setting](https://techcrunch.com/2025/11/04/ios-26-1-lets-you-turn-down-liquid-glass-transparency/)

## 5. Accessibility

Automatic on any system component and on `glassEffect` (WWDC25 219): Reduce Transparency makes the glass frostier and hides more of what is behind it; Increase Contrast renders elements mostly black or white with a contrasting border; Reduce Motion lowers effect intensity and disables the elastic/morph behaviour. You only need to handle your own custom layers: read `@Environment(\.accessibilityReduceTransparency)` (Bool, opaque backgrounds expected when true), `\.accessibilityReduceMotion`, `\.colorSchemeContrast` (`.standard`/`.increased`), `\.accessibilityDifferentiateWithoutColor`, and gate `withAnimation`, `.clear` dimming, and tints on them. Apple's checklist: give every icon-only toolbar item an accessibility label, keep tap targets, test with all three settings and both Liquid Glass looks.

Sources: [accessibilityReduceTransparency](https://developer.apple.com/documentation/swiftui/environmentvalues/accessibilityreducetransparency), [accessibilityReduceMotion](https://developer.apple.com/documentation/swiftui/environmentvalues/accessibilityreducemotion), [colorSchemeContrast](https://developer.apple.com/documentation/swiftui/environmentvalues/colorschemecontrast), [Adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass)

## 6. Backward compatibility

- Building against the iOS 26 SDK is the switch: every standard SwiftUI/UIKit component picks up Liquid Glass automatically on iOS 26 devices (watchOS gets it even without rebuilding).
- `UIDesignRequiresCompatibility` (Boolean, Info.plist, iOS/iPadOS/macOS/tvOS 26): YES renders the app as if built with the previous SDK. Apple: "Temporarily use this key while reviewing and refining your app's UI". It is ignored when you build with the iOS 27 SDK, so it is a one-release bridge, not a design choice.
- If you also ship to iOS 18: wrap with `if #available(iOS 26, *)` inside a `ViewModifier` (e.g. glass capsule vs `.background(.regularMaterial, in: .capsule)`), and use `#available` for `Tab(role:)`/toolbar spacer differences. Since the target here is iPadOS 26 only, set the deployment target to 26.0 and skip the fallbacks; just don't touch the iOS 27 symbols listed in section 2.

Sources: [UIDesignRequiresCompatibility](https://developer.apple.com/documentation/bundleresources/information-property-list/uidesignrequirescompatibility), [Adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass), [Donny Wals: opting out](https://www.donnywals.com/opting-your-app-out-of-the-liquid-glass-redesign-with-xcode-26/)

## 7. iPad specifics: windowing, resizing, pointer, keyboard

**Windowing (iPadOS 26)**
- Every multitasking app now shows a resize handle and window controls at the top-leading corner; controls appear inline on the leading edge of your toolbar, and existing items shift right. Apps not built for 26 get a compatibility safe area above the toolbar, which wastes space. Use `NavigationStack`/`NavigationSplitView` so SwiftUI reserves the space.
- `UIRequiresFullScreen`: deprecated in iPadOS 26 with a console warning that it "will soon be ignored". On iPadOS 26 windowed-apps devices the compatibility mode already means: scene keeps a fixed size, is scaled when resized, can be shown next to other apps, and is not full screen. With the iOS 27 SDK it stops opting out entirely (scenes resize discretely). New key `UIRequiresFullScreenIgnoredStartingWithVersion` (string, **iOS 26.2**) lets you keep the key for older OSes while ignoring it from a given version. TN3192's requirements for a resizable app: a launch screen (mandatory for App Store with the 27 SDK), all four `UISupportedInterfaceOrientations`, no `UIRequiresFullScreen`, and scene-based lifecycle (`UIApplicationSceneManifest`; a warning on 26, required with the next SDK). "Once you build and submit with the iOS 26 SDK, the system will no longer scale or letterbox your app's UI for a new screen size."
- Sizing: `Scene.windowResizability(_ resizability: WindowResizability)` (iOS 17): `.automatic`, `.contentSize`, `.contentMinSize`. Pattern from TN3192 and the Metal-on-iPad guide: `WindowGroup { ContentView().frame(minWidth: 640, minHeight: 360) }.windowResizability(.contentMinSize)`. `defaultSize(width:height:)` (iOS 17) sets the initial size. UIKit equivalent `UIWindowScene.sizeRestrictions?.minimumSize`; Apple states it is a preference, not a guarantee. No published default minimum window size. `windowResizeAnchor(_:)` is documented macOS 26 only despite the WWDC demo.
- Layout: resizing must be non-destructive (WWDC25 208). `horizontalSizeClass` describes the trait environment, not width, and can stay `.compact` after a window grows (fatbobman), so size layouts from `onGeometryChange(for:of:action:)` (iOS 16, back-deployed; transform must be `@Sendable` and return `Equatable & Sendable`) or `containerRelativeFrame`. For Metal/streaming views: keep the current render target size while `UIWindowScene.effectiveGeometry.isInteractivelyResizing` is true and reallocate when it ends; observe `effectiveGeometry` via KVO or `windowScene(_:didUpdateEffectiveGeometry:)`. Orientation lock is a per-view-controller preference (`prefersInterfaceOrientationLocked`), not guaranteed.
- Menu bar: `.commands { }` on the scene builds the iPad menu bar (same API as macOS). Name windows per document.

**Pointer and trackpad**
- `hoverEffect(_ effect: HoverEffect = .automatic, isEnabled: Bool = true)` (iOS 17; the two-arg form is iOS 13.4), `HoverEffect.automatic/.highlight/.lift`, `hoverEffectDisabled(_:)`, `defaultHoverEffect(_:)`, `onHover(perform:)` (iOS 13.4), `onContinuousHover(coordinateSpace:perform:)` (iOS 17). `pointerStyle(_:)` is macOS/visionOS only. HIG: highlight for small transparent-background elements (bar buttons), lift for small opaque ones, hover (custom scale/tint/shadow) for large ones; pad hit regions roughly 12 pt with a bezel, 24 pt without; keep adjacent bar button hit regions contiguous. Glass `.interactive()` already responds to pointer hover.

**Keyboard**
- `keyboardShortcut(_ key: KeyEquivalent, modifiers: EventModifiers = .command)` (iOS 14), `keyboardShortcut(_ shortcut: KeyboardShortcut)`, `KeyboardShortcut.defaultAction` (Return) and `.cancelAction` (Escape), `keyboardShortcut(_:modifiers:localization:)`, `@Environment(\.keyboardShortcut)` for custom button styles. Resolution is leading-to-trailing depth-first in the active scene, then command groups; first match wins. `focusable(_:interactions:)` (iOS 17) for custom focus. HIG: modifier order Control, Option, Shift, Command; don't repurpose standard shortcuts; support Full Keyboard Access.

## 8. Performance for a streaming/real-time app

**Data flow**
- `@Observable` (Observation, iOS 17) tracks per-property reads inside `body`, so a view re-evaluates only when a property it read changes; `ObservableObject` invalidates on any `@Published`. Keep high-rate stats (bitrate, latency, fps) in a separate `@Observable` object from control state so the video surface's parent never re-renders. `Observations<Element, Failure>` (iOS 26) is an `AsyncSequence` over transactional changes; use it for non-UI consumers. The lazy `@State` macro and `@ContentBuilder` are Xcode 27 (TN3211), not in your SDK.
- Isolation: Swift 6.2+ SE-0466 lets you set `.defaultIsolation(MainActor.self)` in `swiftSettings` so a UI module is MainActor by default; SE-0461 makes `nonisolated async` functions run on the caller's actor. Mark decoder/network types `nonisolated` explicitly and hand frames across with `sending`.
- `task(id:priority:_:)` (iOS 15): the task is cancelled when the id changes or the view disappears; make loops `while !Task.isCancelled` and pass `id:` the session identity so reconnects restart cleanly.
- `@Entry` (iOS 13 via macro, SwiftUI 5) for `EnvironmentValues`, `Transaction`, `ContainerValues`, `FocusedValues` entries.

**View updates**
- `EquatableView`/`.equatable()` on heavy subviews whose inputs are value types; `animation(_:value:)` scoped to one value or `animation(_:body:)` (iOS 17) scoped to specific modifiers instead of implicit `.animation` on whole trees; avoid `withAnimation` around high-frequency state.
- `drawingGroup(opaque:colorMode:)` composites a subtree offscreen with Metal; `Canvas` for immediate-mode overlays (no per-element accessibility, faster for dynamic data); `TimelineView(.animation)` or `.periodic` for clocks/overlays instead of timers that mutate state.
- `onGeometryChange` with a cheap `Equatable` transform so scroll/resize doesn't fan out; list/lazy stack improvements in iOS 26 are automatic. Profile with the SwiftUI instrument (Xcode 26; view-body updates and cause-and-effect graph; Instruments in 26.4 adds run comparison).
- Glass: each `glassEffect` is a backdrop sample; keep the count low, one `GlassEffectContainer` per cluster, never place the video surface inside a glass container, and don't animate glass at 120 Hz over the stream.

**Lowest-latency presentation (do this in UIKit via `UIViewRepresentable`)**
- `MTKView` (iOS 9) offers timed, notification, and explicit draw modes (`isPaused`, `enableSetNeedsDisplay`, `draw()`), owns a `CAMetalLayer`, and defaults to 60 fps (`preferredFramesPerSecond`). A forum measurement shows MTKView frames landing one extra vsync late; Apple gave no fix. Prefer a plain `UIView` whose `layerClass` returns `CAMetalLayer.self`: set `pixelFormat`, `framebufferOnly = true`, `maximumDrawableCount = 2` (only 2 or 3 allowed; 3 is the default and adds a frame of latency), leave `presentsWithTransaction = false` (the default presents "as quickly as possible and asynchronously" to Core Animation; `true` is only for syncing Metal content with UIKit overlays and requires `commit()` then `waitUntilScheduled()` then `drawable.present()` instead of `presentDrawable`), call `nextDrawable()` as late as possible inside an `autoreleasepool`, and present via `commandBuffer.present(drawable)`. Drive draws from the decoder's frame callback rather than a display link so a frame goes out the moment it decodes; if you need pacing, `CAMetalDisplayLink` (iOS 17, `init(metalLayer:)`, `preferredFrameLatency` 1.0 or 2.0, `preferredFrameRateRange`) beats `CADisplayLink`. `UIUpdateLink` (iOS 18) `wantsImmediatePresentation = true` presents "one frame duration sooner" (Apple aims it at pencil apps and warns to keep render work minimal); `wantsLowLatencyEventDispatch` is pencil-only. `displaySyncEnabled` is macOS only. Compute `drawableSize` from the view bounds times `contentScaleFactor` (`\.displayScale` in SwiftUI) and, per the iPad Metal guide, don't resize while the user is dragging. Implement `sizeThatFits(_:uiView:context:)` or let SwiftUI size it; never set `frame`/`bounds` yourself. Overlay controls in SwiftUI on top (they are glass; the surface is content).

## 9. What changed in iOS 26.1 to 26.5 and Xcode 26.x

- **iOS 26.1**: `tabViewBottomAccessory(isEnabled:content:)`; `GlassButtonStyle.init(_ glass:)`; user-facing Clear/Tinted Liquid Glass setting; toolbar buttons without explicit labels now show text instead of a symbol (fix). Xcode 26.1 ships Swift 6.2.1 and SDK 26.1.
- **iOS 26.2**: `UIRequiresFullScreenIgnoredStartingWithVersion`. Xcode 26.2 ships Swift 6.2.3, SDK 26.2. Xcode 26.3 (agentic coding) still ships the 26.2 SDK.
- **iOS 26.4 / Xcode 26.4 (24 March 2026)**: Swift 6.3 (`@c` interop, module selectors `Module::name`, `@specialize`, `@inline(always)`, `@export(implementation)`; you will see that last attribute in Apple's rendered declarations, it is an ABI annotation, ignore it), SDK 26.4, big Instruments update (run comparison). No new SwiftUI surface in the 26.4 release notes beyond fixes (`.userActivity` propagation).
- **iOS 26.5 / Xcode 26.5**: SDK 26.5, Swift 6.3.x; only StoreKit `preferredSubscriptionPricingTerms(_:)` is called out. I found no SwiftUI glass or toolbar API added between 26.2 and 26.5; `visibilityPriority` is iOS 27 (macOS 26.1).
- **iOS 27 (WWDC26, do not target)**: refined glass look applied automatically, dimmed inactive windows on iPadOS via `\.appearsActive` (the value exists on iOS 18 but is always true before 27), `toolbarMinimizeBehavior`, `ToolbarOverflowMenu`, `topBarPinnedTrailing`, `Tab(role: .prominent)`, swipe actions on any view, reorderable containers, lazy `@State`, `@ContentBuilder`, `AsyncImage` caching (back-deployed to 17).
