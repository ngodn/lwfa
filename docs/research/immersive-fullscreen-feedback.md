# Fullscreen feedback during immersive mode

Investigated on 9 September 2026, against lwfa 1.5.6.

## Confirmed failure

After entering browser immersive mode, pressing the adjacent window Fullscreen
button could briefly fill the canvas and then restore the column. RE9 session
logs showed X11 enter/leave requests around 80 ms apart, with encoder dimensions
switching between 1389×938 and 1250×914.

The logged requests enter through Smithay's XWM `_NET_WM_STATE` ClientMessage
handler. They are application requests, not browser Fullscreen API events or
property-change notifications generated by the compositor's acknowledgement.
The [EWMH specification](https://specifications.freedesktop.org/wm/latest/ar01s05.html)
describes this request/property distinction.

The relevant chain is:

1. `WindowsPanel.tsx` focuses the window and invokes `toggleFullscreen`.
2. `strip.ts` changes the layout; `App.tsx` sends it to the engine.
3. The engine configures the X11 window's new rectangle.
4. Wine can derive fullscreen state from the window rectangle and send an X11
   fullscreen request. Its `win32u/window.c` and `winex11.drv/window.c` implement
   that conversion. See [Wine's X11 window state handling](https://raw.githubusercontent.com/ValveSoftware/wine/bleeding-edge/dlls/winex11.drv/window.c).
5. `handlers/xwayland.rs` passes the request to `request_fullscreen_x11` in
   `state.rs`, which acknowledges it and broadcasts `fullscreenRequest`.
6. The shell previously applied every request to the same layout state used
   by its own button. An application leave request could undo a user enter;
   an application enter could also undo a user exit.

Browser immersive state stayed enabled throughout. The missing distinction was
between application fullscreen requests and explicit shell placement choices.

## Reproduction

The browser regression in `scripts/e2e-immersive.mjs` uses the real built shell
and actual Fullscreen button. It replays application enter/leave requests 80 ms
apart. Before the fix, one click produced a 1324×900 layout followed by a
1192×876 column layout. The test failed three consecutive times.

A separate local Wine/DXVK fixture reproduced the same path using the shipped
engine and SDK-built patched Wine. The fixture starts windowed, receives the
shell fullscreen rectangle, then requests a four-pixel inset. Wine sends enter
and leave requests without the fixture invoking a fullscreen API. Restoring
the monitor extent whenever the shell returns to a column produces a repeating
loop: 66 enter/leave requests over approximately 16 seconds.

This demonstrates that selecting patched Proton alone cannot prevent this
shell handling bug. It does not establish which RE9 internal operation first
changes its rectangle.

## Fix

Each workspace records which selected window has an explicit shell fullscreen
override. Both directions of the shell button or shortcut hold that choice.
Application requests for that window cannot reverse it. Selecting another
window, removing the window, fitting the workspace, or moving the window clears
the override. A workspace keeps its choice when switching away and back.

Application-controlled fullscreen continues to work when there is no explicit
override. Browser immersive mode is independent. Saved arrangements preserve
the choice only when the existing layout validation accepts their snapshot.
Old snapshots without an override remain supported.

Ignored and duplicate requests return the unchanged state. `App.tsx` does not
send another layout or stream selection for those transitions. This uses state,
not a timer or debounce window.

## Validation and limits

- 736 unit tests passed, including feedback in both directions, viewport
  changes, focus changes within a stack, window removal, and cache restoration.
- Four browser scenarios passed: native fullscreen, rejected fullscreen,
  follower, and standalone. The replay emits zero layout messages after either
  explicit Fullscreen or Exit. Application-controlled enter/exit still works
  before a shell override is chosen.
- Native stress test: 861 H.264 frames stayed at 1389×938 while fullscreen;
  241 frames after explicit Exit stayed at 1250×914.
- Type checking and the shell build passed.

The synthetic app deliberately keeps requesting conflicting rectangles. Native
client sizes still vary by eight pixels and X11 requests still arrive, so its
broader native-size stability check remains false. The fix stops those requests
from changing shell placement. It does not claim to fix every app-side resize
or frame-generation problem. Actual RE9 verification remains pending.

The engine capture, encoder, monitor sizing, and Wine patch code were not
changed by this fix. Tests used disposable sessions; the production service,
host display, installed Proton tools, and game prefixes were not modified.

Local investigation artifacts are under `target/immersive-game-bug/` (ignored):
baseline `run-htensggg`, first candidate `run-j1eskiyw`, final candidate
`run-ysetzgn8`. Browser red and green evidence is under `target/immersive-e2e/`.
